# SNAP Analytics Platform V2 — Production Notes

**Module:** Module 2 — Transformation / Data Quality / Silver Layer  
**Topics:** Data Type Design, Validation Gate, Semi-Structured Source Parsing, Schema Drift, Reconciliation, Pipeline Health

| **#** | **Production Topic** | **中文解釋** | **解決了什麼問題？** | **Production Notes (EN)** | **Interview Takeaway** |
|---|---|---|---|---|---|
| **1** | **Business Meaning → Data Type** | Data Type 應該由 **Business Meaning** 決定，而不是看到資料長什麼樣就決定。例如 Count → Int64、Money → Float64、Text → string。也要理解 nullable dtype，例如 `Int64` vs `int64`、`astype("string")` vs `astype(str)`。 | 避免 Schema 設計錯誤，讓資料模型更符合商業定義。 | Always design data types based on business meaning, not just observed values. Counts should be integers, monetary amounts should be floats, and descriptive fields should be strings. | 「我會先理解欄位的商業意義，再決定 Target Schema，而不是只根據目前資料格式。」 |
| **2** | **Parquet vs CSV & JSON Logs** | Data 和 Log 要分開存。可信資料存 **Parquet**；Validation、Error、Pipeline Log 存 **JSON**。Parquet 可保留 schema / data types。 | 保留完整 Schema，同時讓 Log 容易閱讀、追蹤與監控。 | Store trusted datasets in Parquet to preserve schema and performance. Store validation reports and logs in JSON for readability and monitoring. | 「Production 通常把資料與 Log 分開管理，Data 用 Parquet，Validation Report 用 JSON。」 |
| **3** | **Python Package Execution (`python -m`)** | Production 專案通常以 **Package** 執行，而不是進到資料夾直接跑 `.py`。 | 避免 Import Path 問題，維持專案結構一致。 | Execute production projects as Python packages using `python -m` instead of running individual scripts directly. | 「我會用 `python -m src.pipelines.silver_pipeline`，因為 Production 通常以 Package 執行。」 |
| **4** | **Validation Gate & Failure Path** | Pipeline 不只要測成功流程，也要測失敗流程。Business Validation FAIL 時，Pipeline 應停止發布 Silver、產生 Validation Report，並 raise error。 | 確保只有可信資料會進入 Silver，同時留下可追蹤的錯誤紀錄。 | Production pipelines should validate both success and failure paths. Failed validation should stop publishing, generate a validation report, and raise an exception. | 「我不只測 happy path；critical validation fail 時，我會讓 pipeline fail loudly 並阻止 trusted output 被發布。」 |
| **5** | **Semi-Structured Excel → Logical Table Parsing** | Timeliness 同一個 worksheet 包含 Applications、Redeterminations 兩張 logical tables，另外還有 title、blank rows、TOTAL、notes。應用 business section/header 解析，不 hard-code row number。 | 避免 Excel layout 微調造成 silent parsing error。 | Parse semi-structured reports using meaningful section markers and expected table structure rather than fixed row positions. | 「遇到 semi-structured Excel，我先辨識 logical sections，再建立穩定 parsing rules，而不是 hard-code rows。」 |
| **6** | **Schema Validation & Schema Drift** | Design 階段人工 profile source；production 則由 pipeline 自動確認每個 file / block 是否仍是 `Region / Disposed / Timely / Percent`。 | 不需要人工逐檔檢查，也能發現 upstream schema change。 | Define the expected schema once and automatically validate every incoming file to detect schema drift. | 「Human 定義 expectation，pipeline scale validation；unexpected schema change 應 fail loudly。」 |
| **7** | **TOTAL as Reconciliation Control** | `TOTAL` 不屬於 analytical grain，但在 publish 前可比較 `SUM(detail)` 與 source TOTAL。驗證後排除 TOTAL，避免 double counting。 | 同時驗證 extraction completeness 與 downstream aggregation safety。 | Use source totals as reconciliation controls, but exclude aggregate rows from published analytical datasets to prevent double counting. | 「我不會直接刪 TOTAL；先拿它做 reconciliation，再從 analytical output 排除。」 |
| **8** | **Source Metadata vs Analytical Records** | Titles、notes、definitions 是 source metadata，不是 business record。Bronze 保存完整 source；Silver 排除 presentation metadata。 | Silver 保持 clean grain，同時保留 source traceability。 | Preserve the original source in Bronze while excluding presentation metadata from Silver analytical records. | 「Silver 排除 notes 不代表 source 被刪掉，Bronze 仍完整保存。」 |
| **9** | **Critical Metadata Cross-Check** | Reporting month 同時存在 filename 與 report title，使用 derive + cross-check，而不是盲信其中一個。 | 發現 wrong file、wrong title 或 source metadata mismatch。 | When a critical attribute is available from independent source signals, derive it and use the second signal as a validation control. | 「對 critical metadata，我會 cross-check independent source signals。」 |
| **10** | **Categorical Code ≠ Numeric Measure** | `Region = 01` 看似 numeric，但 business meaning 是 identifier，因此保留 string；`02/09` 更顯示不能當數字。 | 避免 leading zero 消失與錯誤 numeric conversion。 | Determine type from business meaning. Region codes are categorical identifiers even when values appear numeric. | 「我不會看到 `01` 就轉 integer；先判斷它是 identifier 還是 measure。」 |
| **11** | **Undocumented Source Categories** | `CCC / DATA INT / MEPD / PERFORMANC / ST OFFICE / VIC / UNKNOWN` 無可靠 definition。採 **Preserve → Flag → Document → Control downstream usage**，不猜、不直接刪。 | 避免 data loss，也避免未驗證 category 混入 governed geography analytics。 | Preserve undocumented source categories for completeness, flag and document them, and control downstream usage until meaning is validated. | 「不知道的 source value，我會 preserve、flag、document，而不是猜或直接刪。」 |
| **12** | **Transform Only With a Reason** | Normalization 不是看到什麼都改。例如 source terminology 已一致，就不因 cosmetic preference 強制 singular/plural mapping。 | 避免 unnecessary transformations 與額外 mapping risk。 | Normalization should solve a defined consistency or business problem rather than change values for cosmetic consistency. | 「每個 transformation 都要有明確理由，我不會為了 standardize 而 standardize。」 |
| **13** | **Source Metric vs Governed Metric** | `Percent` 改成 `source_percent`，只作 source reconciliation。真正 timeliness rate 從 `timely_count / disposed_count` 計算。 | 避免把 source display metric 直接當 governed KPI。 | Distinguish source-provided metrics from governed analytical metrics. Recalculate rates from base measures and reconcile against the source. | 「我保留 source percentage 作 validation，但 governed rate 從 base counts 計算。」 |
| **14** | **Display Format vs Stored Value** | Excel 顯示 `38.47%` 不代表底層 value 是 `38.47`。Silver canonical rate 存 `0.3847`；`%` 是 BI presentation formatting。Implementation 前要 inspect actual ingested value。 | 避免 percentage 被重複 `/100` 或把 display string 當 numeric data。 | Separate display format, stored source value, and target analytical representation. Inspect the ingested value before applying conversion logic. | 「我會先 inspect source value，再轉型；display formatting 和 stored data 是兩件事。」 |
| **15** | **Validation Severity by Business Impact** | Null / anomaly 不應全部同 severity。Missing grain/base measure → FAIL；missing `source_percent` 但 counts 完整 → WARNING。 | Validation Gate 不會過度 blocking，也不會放過破壞 trust 的問題。 | Set validation severity according to business impact and downstream trust, not anomaly type alone. | 「我會根據是否破壞 grain、metric 或 trust 來決定 FAIL / WARNING。」 |
| **16** | **Duplicate Grain ≠ Simple Deduplication** | `reporting_month + processing_type + region` 預期 unique。Duplicate 可能代表 source duplication、parser error 或 grain 定義不完整，不能直接 `drop_duplicates()` 或 SUM。 | 避免隱藏真正的 modeling / transformation error。 | Never automatically deduplicate at an expected business grain without understanding the root cause. | 「Duplicate key 不是清掉就好；它可能代表 grain 或 transformation 有問題。」 |
| **17** | **Zero Denominator Semantics** | `disposed_count = 0` 時 `timely_count` 必須為 0；rate 應是 `NULL`，不是 0%。`0/0` 表示沒有可評估 population。 | 避免把 no activity 誤解成 0% performance。 | Define zero-denominator behavior from business meaning. No eligible denominator means the rate is undefined, not zero. | 「我會區分 no activity 和 zero performance；兩者的 business meaning 不一樣。」 |
| **18** | **Rate Reconciliation With Precision-Aware Tolerance** | Source 顯示到 percentage 小數 2 位，所以 reconciliation 要考慮 rounding。以 decimal rate 表示時可用約 `0.00005` tolerance。 | 避免因顯示 rounding 造成 false failures。 | Reconciliation tolerance should come from source precision, not an arbitrary threshold. | 「Tolerance 不是隨便設；我會根據 source 的實際 precision 推導。」 |
| **19** | **Profile Before Promoting a Control to a Gate** | TOTAL reconciliation 目前先 profile 12 months × 2 blocks。如果 consistent exact match，再把 mismatch 升成 FAIL；若 source aggregation methodology 不同，先 document / investigate。 | 避免在不了解 source methodology 前建立錯誤 blocking rule。 | Profile source behavior before promoting a reconciliation check into a critical validation gate. | 「我先用 evidence 建 expectation，再把 control 變成 blocking rule。」 |
| **20** | **Pipeline Health Beyond Job Success** | Pipeline 成功執行不代表 healthy。還要看 source completeness、schema stability、business validation、reconciliation、freshness、downstream readiness。 | 避免 technical success 但 business output 不可信。 | Pipeline health includes execution reliability, source completeness, schema stability, data quality, reconciliation, and downstream readiness. | 「我不只看 job status；我會確認今天的 output 是否完整、可信，而且可以安全供 downstream 使用。」 |

## Interview Mental Model

`Expected Business Meaning → Expected Structure → Automated Validation → Severity / Gate → Trusted Silver → Downstream Readiness`
